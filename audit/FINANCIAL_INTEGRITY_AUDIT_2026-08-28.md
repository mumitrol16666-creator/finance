# Аудит финансовой целостности Finance Tracker

Дата: 28 августа 2026 года  
Версия кода: `591dedfdb9ca852236e53b05f65cb2f1ffb44350`  
Область: Telegram-бот, FastAPI, Flutter-приложение, SQLite, валюты, долги, плановые и регулярные операции, депозиты, бюджеты, отчёты и AI-потоки.

## Итог

Сейчас проект нельзя считать безопасным для реальных финансовых данных без исправления критических и высоких проблем.

Баланс действительно может измениться без соответствующего итогового состояния журнала. Это не предположение: несколько сценариев воспроизведены на изолированных временных SQLite-базах. Реальная серверная база и серверные настройки не открывались и не изменялись.

Стандартный security-аудит зафиксировал 17 подтверждённых находок:

- 1 критическая;
- 11 высокой серьёзности;
- 5 средней серьёзности.

Самая срочная проблема вне арифметики: в Git отслеживается полный Telegram bot token, а рядом сохранены диагностические Telegram-ответы и финансовые данные. Секрет в этот отчёт намеренно не скопирован.

## Подтверждённые критические и высокие риски

### P0-1. Telegram token находится в отслеживаемом файле

В `scratch/check_updates.py` найден полный bot token. В `scratch/check_updates_output.json` сохранён успешный ответ Telegram Bot API, то есть токен был рабочим в момент создания файла.

Риск: управление ботом, перехват ожидающих updates, сообщения от имени бота и доступ к чувствительной переписке. Текущая действительность токена по сети не проверялась.

Нужно немедленно:

1. отозвать токен через BotFather;
2. выпустить новый;
3. заменить его на сервере;
4. удалить секрет и Telegram/финансовые дампы из текущего дерева и истории Git;
5. включить secret scanning в pre-commit и CI.

### P0-2. Параллельные update/delete расходят баланс и журнал

`delete_tx` и `update_tx` читают старую транзакцию до `BEGIN IMMEDIATE`. Два параллельных запроса используют одно старое значение и применяют его дважды.

Фактическое воспроизведение:

- исходный расход `−100`, баланс `900`;
- два одновременных DELETE;
- итоговый баланс `1100`, хотя расход удалён только один и правильный баланс равен `1000`.

Второй тест:

- исходная проводка `−100`, баланс `900`;
- два одновременных PUT суммы `200`;
- итоговая проводка `−200`, но баланс `700` вместо `800`.

Источник: `app/db/repositories/tx_repo.py`, функции `delete_tx` и `update_tx`.

### P0-3. Редактирование межвалютного перевода уничтожает курс

Создание перевода правильно хранит две разные суммы, например `−100 USD` и `+45 000 KZT`. При редактировании обе стороны принудительно становятся равны новой исходной сумме.

Фактическое воспроизведение:

- до редактирования: `−100 USD / +45 000 KZT`;
- изменение суммы на `200`;
- после редактирования: `−200 USD / +200 KZT`;
- KZT-баланс уменьшился на `44 800 KZT` только из-за редактирования.

Перенос стороны перевода на счёт другой валюты также выполняется без пересчёта.

Источник: `app/db/repositories/tx_repo.py:267-293`.

### P0-4. Повторные и параллельные денежные действия не идемпотентны

Нет уникального идентификатора исполнения для регулярной операции, planned occurrence, debt payment и периода депозитного начисления.

Подтверждено:

- повторный callback регулярного расхода создаёт второй расход и повторно уменьшает баланс;
- повторный callback регулярного дохода создаёт второй доход;
- старый callback закрытого долга сначала создаёт новую проводку, а обновление долга затем становится no-op;
- два параллельных API-платежа долга могут оба списать деньги, используя старый остаток;
- два параллельных `/planned/{id}/execute` могут исполнить один planned item дважды.

Изолированный тест повторного регулярного расхода: баланс `1000 → 600` при шаблоне `200`, то есть создано две операции вместо одной.

### P0-5. Проценты по депозиту дублируются через GET

`GET /api/dashboard` и `GET /api/accounts` вызывают денежное начисление. Сервис читает старый marker до блокировки и не имеет уникального ключа `(account_id, accrual_date)`.

Фактическое параллельное воспроизведение:

- депозит `120 000`, ставка `12%`;
- два одновременных чтения;
- оба вызова завершились успешно;
- создано четыре процентные проводки вместо двух прошедших периодов;
- начислено `4 824` вместо `2 412`.

Источник: `app/services/deposit_service.py` и `app/api/api_server.py:459,679`.

### P0-6. Telegram-платёж долга использует другую математику, чем API

Telegram:

- не ограничивает списание остатком долга;
- не конвертирует базовую валюту долга в валюту выбранного счёта;
- не создаёт `debt_payments` history;
- допускает повторный callback уже закрытого долга.

Пример: при остатке `1 000` пользователь может провести `10 000`; со счёта уйдёт `10 000`, а долг уменьшится только на `1 000`. Платёж KZT-долга с USD-счёта применяет ту же цифру как USD.

Одиночный API-путь, напротив, делает clamp и FX-конвертацию, но остаётся уязвимым к параллельному stale read.

### P0-7. Удаление или редактирование debt transaction не возвращает долг

API-платёж одновременно создаёт account transaction, уменьшает долг и пишет history. Общие `delete_tx` и `update_tx` меняют только transaction/account balance.

Следствие: пользователь может удалить платёжную проводку, деньги вернутся на счёт, но долг останется уменьшенным или закрытым. При редактировании сумма проводки и `debt_payments.amount` также расходятся.

### P0-8. Telegram-автонакопление не конвертирует валюту

После дохода перевод в копилку вызывает общий `add_transfer` без `to_amount`. Если доходный счёт USD, а копилка KZT, списывается, например, `20 USD`, но зачисляется `20 KZT`, а не пересчитанная сумма.

Обычный Telegram transfer и API transfer умеют вычислять destination amount; автонакопление обходится без этой логики.

### P0-9. Приложение передаёт пароли и токены по HTTP

Flutter hard-code: `http://178.105.162.123:8000`. Через этот URL идут login, register, bearer token, транзакции, долги и AI-chat. Checked-in systemd unit публикует Uvicorn на `0.0.0.0:8000` без TLS.

Если порт доступен напрямую, сетевой посредник может украсть пароль или 90-дневный bearer token и менять финансовые данные. Внешний reverse proxy/firewall в репозитории не описан и фактически не проверялся.

### P0-10. В Git сохранены чувствительные пользовательские данные

Отслеживаемые `scratch/db_dump.txt` и `scratch/check_updates_output.json` содержат финансовые записи, Telegram IDs/usernames/messages и позволяют коррелировать пользователя с финансовыми данными. В отчёте значения намеренно не повторяются.

## Остальные подтверждённые проблемы

### API transaction update

PUT не проверяет положительность суммы и ownership новых account/category IDs.

Воспроизведение:

- расход `−100`, баланс `900`;
- `new_amount = −500`;
- запись остаётся типа `expense`, но получает сумму `+500`;
- баланс становится `1500`.

Перенос на существующий чужой account ID возвращает влияние со старого собственного счёта, не применяет его к чужому из-за user filter, но всё равно записывает чужой FK в transaction.

### Ручная корректировка баланса через API

API читает old balance без `BEGIN IMMEDIATE`. Две одновременные корректировки могут оставить один финальный balance и две adjustment-проводки, рассчитанные от одного старого значения.

Telegram-вариант использует явную транзакцию и в этом отношении безопаснее.

### Planned operations

- API `/done` только архивирует item;
- API `/execute` проводит деньги и архивирует;
- Flutter в одном сценарии сначала отдельным запросом создаёт transaction, затем отдельным запросом вызывает `/done`;
- при ошибке второго запроса transaction уже сохранена, UI сообщает общий failure, а retry создаёт дубль;
- `mark_planned_done` вызывает `executescript` внутри заявленной транзакции, что может преждевременно commit-ить денежную часть;
- Telegram handler использует `row.get(...)` для `aiosqlite.Row`, у которого нет `.get`; текущий путь, вероятнее всего, падает и откатывается до создания transaction;
- `req.is_required or 1` превращает переданный `0` обратно в `1`.

### Recurring operations

Telegram умеет проводить recurring expense/income, но occurrence guard отсутствует. API умеет создавать шаблоны, но endpoint `paid/received/execute` отсутствует — функциональность интерфейсов не совпадает.

### Flutter composite saves

Доход, автонакопление и завершение planned item выполняются несколькими независимыми HTTP-коммитами. Частичный success не компенсируется. Методы update/delete также проглатывают non-200/исключения, после чего экран может показать «успешно».

### Периоды и даты

- бюджеты и часть API строят месяц/день от UTC, а не от timezone пользователя;
- около локальной полуночи Telegram и приложение могут отнести одну операцию к разным дням/месяцам;
- объявленный API `date_override` игнорируется;
- AI `date_offset` («вчера») сохраняется в draft, но теряется перед записью;
- операция записывается текущим UTC временем.

### Бюджеты и мультивалютность

API dashboard конвертирует расходы в базовую валюту. Telegram budgets/limits и ряд report SQL суммируют raw amounts разных валют.

Пример: `100 USD` и `10 000 KZT` могут быть показаны как `10 100 KZT`. Из-за этого приложение, Telegram и AI дают разные spend/limit/net worth.

## Аудит AI-промптов

### Что сделано хорошо

- report prompt запрещает придумывать факты;
- отдельно различает net за период и общий account balance;
- требует маркировать уверенность;
- report/chat сами не имеют прямого balance-write;
- single quick-add draft дополнительно проверяет `kind` и `amount > 0`;
- AI draft требует явного подтверждения пользователя;
- при отсутствии OpenAI key существуют локальные fallbacks;
- voice temp file удаляется в `finally`.

### Что опасно

#### Невалидированный batch quick-add

`parse_quick_add_ai` только выполняет `json.loads`. Для batch:

- нет строгой схемы;
- нет `amount > 0` и верхнего лимита;
- любой `kind`, кроме точного `expense`, считается `income`;
- каждый элемент commit-ится отдельно;
- один плохой элемент не откатывает уже сохранённые;
- `account_hint` и `date_offset` игнорируются;
- preview использует KZT по умолчанию.

После подтверждения отрицательный expense может увеличить баланс, а отрицательный income — уменьшить.

#### Смешение валют в AI context

Core AI context не получает currency каждой transaction и складывает raw amounts. Одновременно payload содержит отдельные converted metrics. Модель получает противоречивые цифры.

Отдельный `financial_analysis_engine` использует другой FX-provider и при ошибке молча считает raw amount базовой валютой 1:1. Корректный system prompt не может исправить неверные входные числа.

#### Prompt injection через пользовательские поля

Transaction notes/categories и история чата входят в payload как пользовательские данные, но system prompt явно не говорит считать вложенный текст недоверенными данными, а не инструкциями. Это может исказить совет. Прямого balance-write у report/chat нет, поэтому это hardening, а не подтверждённое списание.

#### Передача чувствительных данных третьей стороне

OpenAI может получить до 60 transactions с датой, суммой, категорией и raw note, account names/balances, debts, recurring/planned operations, цели, профиль поведения и историю чата. Voice отдельно передаётся transcription API.

Нужны field allowlist, PII-redaction, aggregate-only mode по умолчанию и явное disclosure/consent.

## Что работает правильно в последовательном сценарии

- обычный income/expense создаёт transaction и balance delta на одном соединении до commit;
- нормальный transfer create атомарно создаёт две связанные legs и два balance delta;
- последовательное удаление transfer использует фактические суммы обеих legs и возвращает исходные balances;
- ручная корректировка создаёт отдельную `adjustment` transaction;
- starting balance записывается отдельной transaction;
- API dashboard использует правильную формулу DB FX: `to_rate / from_rate`;
- серверная и Flutter формулы USD-relative conversion совпадают;
- parser денег отвергает ноль и отрицательные значения на основных ручных формах;
- один API debt payment корректно clamp-ится и конвертируется при отсутствии гонки.

Изолированный положительный тест подтвердил:

- transfer `100 USD → 45 000 KZT`;
- после удаления balances полностью восстановились;
- `USD → KZT = 450`, `KZT → USD = 1/450` при заданном rate snapshot.

## Проверка живой базы

Для безопасной read-only проверки подготовлен `audit/read_only_integrity_checks.sql`. Он включает `PRAGMA query_only = ON` и ищет:

- расхождение `accounts.balance` и суммы активного ledger;
- cross-user account/category references;
- неверные signs income/expense;
- повреждённые transfer pairs;
- дубли депозитных процентов;
- удалённые/missing debt payment transactions;
- подозрительные повторные денежные записи;
- foreign-key violations и неверные exchange rates.

Перед запуском всё равно следует сделать backup и открыть отдельную read-only копию production DB.
